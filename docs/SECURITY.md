# Security and credential model

## What claude-hr protects, and what it cannot

| Asset | Control | Limit |
|---|---|---|
| `.env`, ssh/cloud/gh credentials via Claude's **file tools** | `permissions.deny` baseline (`credentials.block_secret_reads`) | Deny rules are not a boundary for Bash or for scripts that open files themselves |
| Secrets printed by **Bash / PowerShell** into the transcript | `PreToolUse` guard in `hr-core` (`claude-hr-hook bash-guard`, ~0.15 s per call; blocks printing or exfiltrating `.env`, private keys, cloud/gh credential files, `printenv`/`env` dumps, `echo $TOKEN`, `gh auth token`, `op read`, `/proc/*/environ`; allows `cp .env.example .env`, `process.env`, public keys, `ssh/config`) + deny `Bash(printenv *)`, `Bash(env)` | Pattern-based; a determined indirect read (`python -c 'print(open(".env").read())'`) is not caught. Keep the OS-level sandbox on where it exists |
| Secrets already in plaintext transcripts (`~/.claude/projects/**/*.jsonl`) | `creds scan` (weekly job too): token-shaped strings, reported masked, never printed | Detects well-known token shapes only. Rotate anything found, then delete the file |
| Auth shadowing | `creds doctor` warns when `ANTHROPIC_API_KEY` overrides the subscription login | — |
| Plaintext secret stores | `creds doctor`: `settings.json` env, literal MCP env values, `gh` token in `hosts.yml`, loose permissions on `.credentials.json` (POSIX) | Windows file ACLs are inherited from the profile; not inspected |
| A repository's own commands (`.claude/hr-verify.toml`, run unattended at the end of every turn) | Never run until a person trusted the file's exact bytes (SHA-256 per repository, any edit revokes it). Since 0.2.1 the person is offered the exact commands at launch: when they start an interactive `claude-hr` session in a git repository in a normal terminal (never in `-p`, `agents`, a subcommand, a Claude Code shell or with piped input), the launcher asks once per folder, with a one-keystroke answer (`claude-hr-ctl verify enable` is the same on request). For a folder without a recipe it shows the commands discovery found, runs each once while the person watches, keeps only those that exit 0, writes them with the no-symlink writer, hashes exactly the bytes it wrote and trusts that hash; the default answer is No when the audit preflight finds anything high or medium. A recipe that ships with the repository (a clone, an edit) is shown exactly as `verify trust` shows it (every check of both tiers, escaped, the audit preflight, the SHA-256) with No as the default, and only those displayed bytes are trusted. Nothing about the model changed: there is no flag or environment variable that answers the question, the approval is still the hash of the file, and the question is refused without a person at a terminal. `verify trust` has no `--yes`; it refuses a shell that belongs to a Claude Code session or has no terminal, shows every check of both tiers in full (numbered, with terminal and bidi characters escaped visibly) and the file's SHA-256, and trusts exactly the bytes it showed (it refuses if the file changed during the prompt). `verify run` of an untrusted recipe is refused the same way; the bash guard denies an agent that types `verify trust` / `untrust` / `enable` / `disable` or touches the trust record or the offer record (`state/verify-offer.json`, which only remembers a "no" and never approves anything); the baseline asks before Claude edits the recipe, `.claude/settings*.json` or claude-hr's `config.toml`, and denies edits of claude-hr's `state/` directory (it follows `CLAUDE_HR_HOME`). Checks run without a shell, with a deny-list-scrubbed environment (credential-looking names containing TOKEN, SECRET, PASS, KEY, CRED, AUTH, COOKIE, DSN, CONNECTION, PRIVATE or CERT; the ANTHROPIC_, CLAUDE_CODE_, AWS_, AZURE_, GOOGLE_, GCP_, GITHUB_ and GH_ prefixes (AWS_REGION and AWS_DEFAULT_REGION stay); npm token, auth and password settings; DATABASE_URL; SSH_AUTH_SOCK, GIT_ASKPASS and SSH_ASKPASS; URL values carrying credentials. `PWD` is set to the check's directory. Names you list in `verify.env_allow` are kept), a per-check and an overall time limit, and the process tree ended on timeout and also when a check exits leaving children running (process group on POSIX, job object on Windows; on POSIX a SIGTERM or SIGHUP to the hook ends the running check too, a SIGKILL does not); `verify init --write` never writes through a symlink or junction at `.claude` or `.claude/hr-verify.toml`, and the recipe and discovery manifests are read only if they are regular files; executables are looked up only through absolute PATH entries, never in the repository or the current directory (git is resolved the same way) | Pattern checks, not a boundary: an agent that allocates a pty, obfuscates the command or runs with permission prompts off can still get a recipe trusted (the launcher's question has the same limit: a process that fakes a terminal and unsets `CLAUDECODE` can answer it). The offer runs before Claude Code's own folder-trust prompt, and a folder without a recipe gets Enter = Yes when the audit finds nothing, so in a folder you do not trust answer `n`: the commands are run once, there and then, exactly as you would run the project's tests yourself, and `config set` is guarded only by Claude Code's permission prompts. A trusted recipe's `.cmd` shims use cmd.exe's own lookup on Windows. An edit someone else makes while the checks run is not verified until the next change. The permission prompts, your own review of the recipe, and running untrusted repos in a VM are the real controls |
| Planted executables (a `git.exe`, `op.exe` or `node.exe` committed to a cloned repository; Windows searches the current directory before PATH) | Every bare command claude-hr spawns (git, claude, op, the resource-limiter prefix, taskkill by absolute path) is resolved through absolute PATH entries only, never the current directory or a relative PATH entry (`procutil.resolve_exe`); the formatter's environment sets `NoDefaultCurrentDirectoryInExePath` (the checks' environment does not, because trusted `.cmd` scripts may call siblings by bare name) | A trusted recipe's own `.cmd` shims use cmd.exe's lookup |
| Code that the formatter step would run | The gate formats unattended, so it must not turn "a file was written" into "that file runs". A formatter binary committed to git is always refused. A formatter that lives inside the repository (`.venv`, `node_modules/.bin`: untracked, so an agent with write access only can create one) and **prettier** (its configuration can load code: JS/TS configs, `plugins`, shared config packages, a `parser` that is a path) are refused unless the repository is trusted (its verify recipe was approved) or `format.repo_tools = "always"`. Prettier's configuration is deliberately not vetted by reading it: two attempts (a denylist, then an allowlist) were each found by review to differ from prettier's own parsers somewhere (JSON escapes, YAML scalars, padding, duplicate keys), so there is no check to bypass. Ruff, black, gofmt and rustfmt from your PATH are used with the repo's configuration, which is data (biome is only ever found in `node_modules/.bin`); until a repository is trusted, a ruff or black on your PATH is used even when the project has its own copy in `.venv` (it may be a different version than the one the project pins; the clean gate limits the harm for tracked files, untracked files are always formatted), and a PATH entry that points into the repository, such as an activated `.venv`, does not count as a global tool | Once a repository is trusted, its formatter and configuration are trusted with it (an agent can then add a `prettier.config.js` that the gate runs: the same exposure as the tests the trusted recipe runs) |
| Untrusted repository agent surface (hooks, `enableAllProjectMcpServers`, `apiKeyHelper` and other command-running settings, `CLAUDE_HR_*` or code-loading keys in settings `env`, plugin auto-install, hidden Unicode, injection text in CLAUDE.md and skills, risky workflows, committed secrets) | `claude-hr-ctl audit` and the preflight shown by `verify trust`: read-only, never executes repository code, findings never echo repository text (file names are shown with whitespace as `_`, anything outside a safe set as `?`, names capped at 40 characters), every external scanner runs with a scrubbed environment and a time limit; names match case-insensitively on every OS, every case variant of a hook script is analysed; a hook is judged by its arguments (deleting, creating or changing files outside the project, `git -c`, injection variables in a command prefix, a URL or an exec option passed to an otherwise local tool are findings), hook scripts are followed to depth 4 (24 scripts per hook), a longer chain is reported; a symlink or junction that points at an ancestor (`.claude -> .`) cannot hide the agent surface (the linked content is audited under the name Claude Code reads it, and the link is a finding), any link leaving the repository under `.claude/` or `.github/` is flagged; agent-surface files are never skipped by the ordinary-file cap, and a truncated, unlistable or unreadable scan is itself a finding (an execute-only `.claude` is probed by name; a cut `node_modules` search is reported when git says the directory belongs to the repository); the preflight has its own 20 s budget and says when it is incomplete; a committed `.claude/settings.local.json` is the repository's, not yours, and keeps full severity; exit code 2 means the audit could not run | Pattern checks, not proof; working tree only, not git history; obfuscation beyond base64 / pipe-to-shell is not covered; task runners (`make`, `npm run`) are not followed into their Makefile or package.json; scanners reach their own services (npm registry, OSV) and read repo-supplied config. The hooks, the stop gate and the config loader still read `CLAUDE_HR_*` switches (`GUARD_OFF`, `GIT_GUARD`, `GATES`, `FORMAT__REPO_TOOLS`, ...) from the process environment, which a repository's project settings can set: the audit flags every `CLAUDE_HR_*` key in project settings (high), nothing ignores them yet. Text in a skill, agent or command that tells the agent to skip confirmations is a medium `skill-ignore-rules` finding by design |
| Destructive git commands | The bash guard asks before `--no-verify`, force-push of a protected branch, `reset --hard`, `clean -f`, `checkout .` (`security.profile = "strict"`: refuses); `gh auth token` and `gh auth status --show-token` are blocked | A regex is not a boundary (`F=--force; git push $F origin main`, `sh -c '...'` get past it). Server-side branch protection is the control |
| LLM reviews | `security-guidance`'s per-turn Opus review is off by default (`security.stop_review`); `/security-review`, `/code-review` and the `hr-review-changes` workflow run on request | Advisory only and prompt-injectable: never run an LLM review with write access on untrusted pull requests; deterministic checks and CI are the merge gate. The workflows' finder, skeptic and review agents are told the diff is data and to stay read-only, but they are prompt-restricted, not tool-restricted (they need `git diff`; no read-only agent type exists for that): do not run them on an untrusted PR checkout |
| Headroom CCR store | Holds **plaintext originals of compressed tool output** (`~/.claude-hr/headroom`); doctor checks mode 700 on POSIX | Treat the directory like the transcripts |
| Third-party plugin code | Plugins run with your privileges. Plugins come from Anthropic's SHA-pinned catalog and this repo (third-party entries such as Ponytail are vendored there pinned to a 40-char commit); the one exception is `headroom-snip` from Headroom's own repository. `plugins sync` never installs unlisted plugins. Unattended updates never pass `-y`, so a marketplace-declared command is never auto-accepted; after a self-update the unattended job re-applies only the settings baseline and the CLAUDE.md block (reversible, ownership-tracked merges) and never installs a plugin or adds a marketplace: plugin installs happen only in interactive `setup` / `plugins sync` | Updates follow Anthropic's pins; review `plugins audit` after updates |
| Update supply chain | 5-day cooldown on Headroom releases; Claude Code releases publish per-platform SHA-256 checksums and a detached signature (the installer verifies them); `uv` resolves from PyPI | A compromised release older than the cooldown still installs. Pin versions in regulated environments |
| Network exposure | The proxy binds `127.0.0.1` by default; any other `headroom.host` is your explicit choice and needs Headroom's `HEADROOM_PROXY_TOKEN`. Health checks ignore `HTTP(S)_PROXY` for loopback | — |
| Skills that pre-approve commands | `hr-status` pre-approves only an explicit list of read-only `claude-hr-ctl` verbs (a test enforces that no skill grants a wildcard over `claude-hr-ctl`, `config`, `setup`, `verify trust` or anything that writes) | Pre-approval applies while the skill is active |
| claude-hr itself (unattended self-update) | The daily job checks out the newest `vX.Y.Z` tag of the origin repository (or a branch, if `self.update_ref` names one) and reinstalls it with uv: no cooldown, no tag-signature check, no smoke test, no rollback | A compromised maintainer account, or a fork you point `CLAUDE_HR_REPO_URL` at, runs code as you within a day. Mitigate: `updates.enabled = false` or `claude-hr-ctl update --only claude headroom plugins`, install a pinned `--ref`, review any fork before using it |
| Telemetry | claude-hr sends nothing. Headroom beacon off; Claude error reporting off; `claude.privacy = "strict"` also disables telemetry and non-essential traffic | `strict` removes flag-gated features |

## The end-of-turn gate and trust
`claude-hr-hook stop` (plugin `hr-gates`) formats the files git reports as changed in the working tree (Claude's, and any uncommitted or untracked file of yours) with the repo's own configured formatter and runs the
repo's trusted fast checks. It adds nothing to the context unless a trusted check failed, never blocks on its own errors
(every failure exits 0), skips subagents and plan mode, and keeps a metadata-only trail in `~/.claude-hr/audit` (month files,
owner-only, no code, no output, 90 days). The formatter step only uses a tool the repo configures (ruff, black, prettier, biome,
gofmt, rustfmt), refuses a formatter binary that is committed in the repo, and rewrites a tracked file only when its committed
version was already clean. The test step is the trust decision described in the table above: **the recipe is the repository's
text, so approving it is approving code execution on every turn.** Read it before `verify trust`; `claude-hr-ctl audit` shows
what else in that repository touches the agent surface. Be aware of what a trusted recipe means: its commands run the
repository's own code, including whatever Claude edited that turn (that is what running tests is), and the gate is not part of
Claude Code's permission system. Under `acceptEdits` an edit to a test, a `conftest.py` or a `package.json` script is auto-approved
and the gate then runs it. Run work you do not trust in a VM or container, and trust a recipe only for repositories you would run
the tests of yourself.

## Where credentials come from (recommended order)

1. **Claude Code**: interactive `/login` once per VM (subscription), or on a headless VM `claude setup-token` and supply the
   token as `CLAUDE_CODE_OAUTH_TOKEN` from your secret manager. Do not share one person's token across a team. Do not leave
   `ANTHROPIC_API_KEY` exported unless you intend API billing. Never put tokens in `settings.json` `env`.
2. **Injecting secrets**: set `credentials.op_env_file` and claude-hr launches `op run --env-file=<file> -- claude …`, so the
   secrets exist only in the child's environment. Optionally add `claude`'s `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` via
   `security.profile = "strict"` (strips credentials from Bash/hook/MCP subprocesses; it deliberately keeps `GITHUB_TOKEN`).
3. **GitHub**: `gh auth login` (OS keyring) + `gh auth setup-git`; headless: a fine-grained PAT scoped to the repositories needed,
   read-only by default, 30–90 day expiry; or a per-VM SSH deploy key. Classic and org-wide PATs are not used.
4. **MCP**: prefer OAuth; otherwise `${VAR}` expansion; never `claude mcp add --env TOKEN=literal`.

## Private forks: the clone PAT
For a private fork only, `CLAUDE_HR_GIT_TOKEN` (installer clone only) is passed as a per-command `http.extraheader`; it is not written to `.git/config`,
shell history (when exported from a secret manager), or any claude-hr file. The scheduled self-update uses whatever git
credentials the VM already has (SSH deploy key recommended). If it cannot fetch, it logs `no release tag yet`/fetch failure
and leaves the installed version running.

## Running `--dangerously-skip-permissions`
It stays available (it is an intended workflow). Deny rules and the Bash guard still apply in that mode. Use it in a VM or
container, not as root, not on a machine holding production credentials. `security.profile = "strict"` disables the flag
fleet-wide through `disableBypassPermissionsMode`.

## Reporting
Report vulnerabilities privately through GitHub: the repository's **Security** tab, then **Report a vulnerability**
(https://github.com/timchrist49/claude-hr/security/advisories/new). If that is unavailable, open an issue that says only that
you need a private channel and leave out the details. Do not paste transcripts or `creds scan` file lists into issues
without redacting.
